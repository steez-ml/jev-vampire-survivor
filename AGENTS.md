# Project guidance

## Current milestone

v1 polar pilot. Load through BepInEx 6 IL2CPP (`winhttp.dll`). Keep MelonLoader’s `version.dll` disabled — it crashes this Unity 6 install in `coreclr.dll`. `UnityLogListening = false`. Never retry Unity `AddComponent`.

The in-game DLL is read-only: Harmony postfix on existing `GameManager.Update`, v4 UDP snapshots at ~20 Hz (3×8 polar bins for enemies, XP and walls fitted to the visible camera; inner enemies with velocity; bosses; chests; player level/XP/magnet/facing/weapons and Phaser body blocked sides), compact overlay HUD plus a player-centered field overlay. v4 is additive over v3 — every new field is optional and every new read is isolated (fails once, logs, disables itself). The Python pilot owns transport consumption, memory (stuck detector, wall memory, mode and heading hysteresis), the 8-way scoring (priced contact, phase dial, openness, kiting, walls, weapon aim classes, modes), WASD `SendInput`, and arm/focus/pause gates. Tap Ctrl to arm (toggle). `VSJEV_NUDGE` and `--mode` still override. Jev stays out of this phase; when it arrives it picks a mode, never a key.

## Rules

- Explain C# and game-modding concepts in plain language for a data engineer who is new to Unity and IL2CPP.
- Do not add menu selection, cheats, or gameplay mutations. WASD is allowed only through the gated Python loop.
- Do not invent Vampire Survivors class names or fields. Inspect the assemblies generated by this exact game installation (`BepInEx\interop`) before using game-specific types.
- Keep Jev out of the in-game mod. The future Jev caller belongs in the external bridge so API keys, retries, and policy code do not run inside the game process.
- Keep deterministic safety rules in code. Jev should make narrow semantic decisions from a normalized state rather than perform frame-by-frame collision avoidance.
- Never commit API keys, local game paths, generated assemblies, or runtime logs.
- Every meaningful change should have either an offline check or a clearly stated reason why it must be tested in the game. Policy changes get a `bridge/vampirejev/sim.py` scenario or a `tests/test_policy.py` case; new game reads get an evidence line in the `PlayerPositionProbe` doc comment.
- Weapon knowledge stays at the "aim class" level (facing / movement / auto). No DPS estimation.
